🔐 Android Security and Privacy

Android App Security Best Practices

Most Android security incidents come from a handful of repeat mistakes: secrets in the APK, sensitive data in logs or plain storage, exported components, unsafe WebViews, and trusting the client. This guide organises Android security into practical layers, with code for each.

Android gives every app a strong sandbox, but the sandbox can't protect you from your own design decisions. Security has to be built into how you store data, talk to servers, expose components and handle authentication, and it has to assume the device and the APK can be inspected by an attacker.

Security layers

Core principles

  • Never trust the client. Enforce authorisation, prices, limits and business rules on the server.
  • Minimise data: collect, store and log only what you need.
  • Least privilege: request minimal permissions, and export minimal components.
  • Defence in depth: combine controls, because each one can fail.

Network security

Never ship a custom TrustManager that accepts all certificates or a HostnameVerifier that returns true. Consider certificate pinning only with a rotation plan. See Certificate Pinning.

Data storage

  • Keep sensitive data in app-private storage, never on shared external storage.
  • Encrypt secrets and sensitive data with Keystore-backed keys. See Encrypted Data Storage and Secure Token Storage.
  • Exclude sensitive files from backups.
  • Clear user data on logout.

Secrets

Anything in the APK is extractable, including BuildConfig fields, resources, native libraries and obfuscated strings. Keep real secrets on servers and use short-lived, scoped tokens. See Secure API Keys and Secrets.

Components and intents

  • Use PendingIntent.FLAG_IMMUTABLE unless mutability is required.
  • Use explicit intents for internal communication.
  • Protect custom permissions with signature protection level when sharing between your own apps.

WebViews

  • Keep JavaScript disabled unless needed. Never enable file access from file URLs.
  • Load only your own trusted HTTPS content, and restrict navigation to allowed hosts.
  • Avoid addJavascriptInterface with untrusted content. Prefer WebViewCompat.addWebMessageListener with origin allow-lists.

UI and logs

  • Never log tokens, OTPs, personal data or full API responses in release builds.
  • Mark password fields correctly (KeyboardType.Password or the password input type) so keyboards don't learn them.

Release and supply chain

  • Enable R8 (it raises the effort of reverse engineering, but isn't a security boundary).
  • Use Play App Signing, and protect upload keys. See App Signing.
  • Keep dependencies updated, remove unused SDKs, and review SDK data collection.
  • Use Play Integrity on the server for high-value actions.

Priorities by app type

Content app

TLS, minimal permissions, no secrets in the APK, safe WebViews.

Commerce app

Plus server-side price and order validation, secure tokens, and Play Integrity for checkout.

Finance or health app

Plus encrypted storage, FLAG_SECURE, biometrics for sensitive actions, strict logging, and regular security testing (MASVS).

Frequently asked questions

Does obfuscation make my app secure?

No. It slows reverse engineering. Security comes from server-side enforcement, proper storage and not shipping secrets.

Should I detect rooted devices?

Client-side root detection is easily bypassed. Prefer server-side Play Integrity verdicts for risk decisions, and don't break the app for legitimate users without reason.

Where can I find a complete checklist?

OWASP's Mobile Application Security Verification Standard (MASVS) and testing guide are comprehensive references.

Conclusion

Android security is layered: server-side authority, TLS-only networking, sandboxed and encrypted storage, minimal exported components with validated input, safe WebViews and logging, and a secure release pipeline. Fix the common mistakes first, then deepen for higher-risk apps.
