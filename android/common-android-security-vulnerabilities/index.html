🔐 Android Security and Privacy

Common Android Security Vulnerabilities

Security reviews of Android apps keep finding the same classes of bugs. Knowing them, and seeing what vulnerable code looks like next to the fix, is the fastest way to stop shipping them.

Most real-world Android vulnerabilities aren't exotic exploits. They're configuration and design mistakes: a component exported by accident, a token in logs, a WebView that loads anything. Here are the most common ones, how attackers use them, and how to fix them.

1. Hard-coded secrets

Risk: keys extracted from the APK and abused. Fix: keep secrets server-side, and restrict any client keys. See Secure API Keys.

2. Accidentally exported components

Audit every exported="true". Exported components must validate all input and should not perform sensitive actions without authentication.

3. Intent redirection

4. Mutable PendingIntents

A mutable PendingIntent with an implicit base intent can be hijacked by another app to act with your app's identity.

5. Insecure WebViews

Never combine addJavascriptInterface with untrusted content.

6. Insecure storage and backups

Risk: tokens or personal data in plain files, on external storage, or in backups. Fix: app-private storage, Keystore-backed encryption, and backup exclusions. See Encrypted Storage.

7. Weak network security

Use the platform defaults, Network Security Config, and no cleartext traffic.

8. Sensitive data in logs and screenshots

Fix: remove debug logging of tokens and personal data from release builds, and use FLAG_SECURE on screens showing sensitive data.

9. Trusting the client

Risk: prices, feature unlocks or user IDs accepted from the app. Fix: the server computes and authorises everything, using verified identity tokens and Play Integrity for high-value actions.

10. Path traversal with file names from outside

Building it into your process

  • Enable lint security checks and treat them as errors.
  • Add a security section to your PR template (exports, intents, storage, logging).
  • Run periodic reviews against OWASP MASVS for sensitive apps.
  • Keep dependencies updated, and watch for security advisories.

Quick triage

Before every release

Grep the manifest for exported components, check logging, and confirm no secrets in the build.

New WebView feature

Host allow-list, JavaScript only if needed, no file access.

New deep link

Validate parameters, and authorise on the server.

Frequently asked questions

Does Google Play scan for these issues?

Play performs some automated checks and may warn about known vulnerable patterns, but you remain responsible for your app's security.

Is Kotlin safer than Java here?

Kotlin prevents some bugs (null safety), but these vulnerabilities are about design and configuration, which apply in any language.

Where should a small team start?

Secrets, exported components, logging and TLS. They're quick to check and cover many real incidents.

Conclusion

Most Android vulnerabilities come from untrusted input reaching privileged code or sensitive data leaking out. Minimise exports, never forward intents, use immutable PendingIntents, lock down WebViews and TLS, protect storage and logs, and keep the server as the source of truth.
