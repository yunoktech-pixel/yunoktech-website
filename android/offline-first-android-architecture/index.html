Offline-First Android App Architecture

Offline-first means the app works fully from local data and syncs with the server when it can. Users get instant screens and no lost work on bad networks. Here's the architecture, the sync strategies and the UX details that make it work.

A field agent fills in an inspection form in a basement with no signal. A traveller checks their itinerary on airplane mode. A shopper on a crowded network taps "add to cart". In an online-only app, all three see spinners or errors. In an offline-first app, they don't notice the network at all.

Core principles

  • The local database is the single source of truth. The UI reads only from it.
  • Writes go local first, then sync to the server in the background.
  • Sync is a separate, resilient process (WorkManager), not part of a screen.
  • Conflicts have an explicit policy.

Tracking local changes

Client-generated IDs mean new items can be created and referenced offline, without waiting for a server ID.

The sync worker

With ExistingWorkPolicy.KEEP, a change made while a sync is already running waits for the next sync. APPEND_OR_REPLACE queues a follow-up run instead. Pick the policy that fits your sync frequency.

Conflict resolution strategies

StrategyHowGood for
Last write winsNewest timestamp or version winsSimple personal data, low conflict risk
Server winsLocal change discarded on conflict; user notifiedShared, authoritative data (inventory)
Field-level mergeMerge non-overlapping field changesForms and records edited on several devices
User resolvesShow both versionsDocuments where losing edits is unacceptable

Offline UX

  • Show a subtle "Offline: changes will sync" banner, not an error.
  • Mark unsynced items (a small clock icon), and show failures that need action.
  • Disable only the features that truly need the network, such as payments, and explain why.
  • Show "last updated" times for data that may be stale.

Where offline-first matters most

Field work

Inspections, deliveries and surveys in areas with poor coverage.

Productivity

Notes, tasks and to-do apps, where users expect instant saves.

Content

News or courses downloaded for later, with progress synced when online.

Frequently asked questions

Does every app need to be offline-first?

No. Real-time features such as payments, live bidding and video calls are inherently online. But caching reads and preserving user input help almost every app.

How do I handle deleting items that were never synced?

If an item was created locally and deleted before syncing, remove it locally and skip the server call entirely.

Can I use Firestore's offline persistence instead?

Yes. Firestore provides built-in offline caching and sync. It trades control and portability for convenience.

Conclusion

Offline-first architecture makes the local database the source of truth, writes locally with pending-sync metadata, syncs through a WorkManager worker with backoff, and resolves conflicts with an explicit policy. The result is an app that feels instant and never loses user work.
