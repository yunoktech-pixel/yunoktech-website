🧪 Testing, Debugging, and Performance

MockK vs Mockito for Kotlin Testing

MockK was built for Kotlin; Mockito comes from Java but works well with mockito-kotlin. Both can mock suspend functions and final classes today. The bigger question is often whether you should be mocking at all.

Kotlin classes are final by default, suspend functions take hidden continuation parameters, and top-level functions and objects aren't ordinary Java classes. Early Mockito struggled with all of that, which is why MockK became popular in Android. Both libraries have matured, so the choice is now mostly about style.

Often better: fakes

When mocks are the right tool

  • Verifying a side effect happened exactly once (analytics event, logger call).
  • Third-party classes that are hard to fake and that you don't wrap.
  • Simulating rare failures in deep collaborators.

Team recommendations

Kotlin-only Android app

MockK for its Kotlin-native API, with fakes for repositories.

Mixed Java/Kotlin codebase

Mockito with mockito-kotlin keeps one library for both languages.

Large test suites

Prefer fakes. Measure mock initialisation cost if tests feel slow.

Common mistakes

  • Mocking data classes and value types. Just create real instances.
  • Relaxed mocks everywhere, which hide missing stubs and let tests pass vacuously.
  • Verifying every call, which breaks tests on harmless refactors.
  • Mocking the class under test.

Frequently asked questions

Can I use both in one project?

You can, but pick one as the standard to keep tests consistent.

Do I need special setup for final classes with Mockito?

Recent Mockito versions use the inline mock maker by default, which supports final classes. Older setups needed explicit configuration.

What about mocking Android framework classes?

Avoid it. Wrap framework calls behind your own interfaces, or use Robolectric when you need real behaviour.

Conclusion

MockK offers the most Kotlin-native API, and Mockito with mockito-kotlin is equally capable for most needs. For your own repositories and data sources, fakes usually produce clearer, more robust tests than either.
