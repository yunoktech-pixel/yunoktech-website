🔐 Android Security and Privacy

Encrypted Data Storage in Android

Android already encrypts user data at the device level, but app-level encryption adds protection for specific sensitive data against backups, extraction and some compromised-device scenarios. Here's what to encrypt, the modern tools to do it with, and how to migrate off deprecated libraries.

Modern Android devices use file-based encryption: data at rest is encrypted, and apps' private directories are protected by the sandbox. So why encrypt again? Because device encryption protects a powered-off, locked device, not your app's data from backups, debugging tools on compromised devices, or another layer of defence your compliance team requires.

What to encrypt at the app level

DataEncrypt?Notes
Auth tokens, session secretsYesSee Secure Token Storage
Health, financial, identity documentsYesOften required by policy or regulation
Private user content (journals, private notes)OftenConsider user expectations
Cached public content, preferences like themeNoEncryption adds cost without benefit

About EncryptedSharedPreferences and EncryptedFile

Jetpack Security (androidx.security:security-crypto), which provided EncryptedSharedPreferences and EncryptedFile, has been deprecated. Existing apps keep working, but new code should use alternatives such as Tink directly (which security-crypto used internally), together with DataStore or files. Plan a migration that reads old values once and re-writes them with the new mechanism.

Encrypting files with Tink

In production, create the primitive once and reuse it. For small values, use Tink's Aead with a DataStore serializer, as shown in Secure Token Storage.

Encrypting a Room database

Room doesn't encrypt by itself. A common approach is SQLCipher, which plugs into Room through an openHelperFactory. Protect the database passphrase by generating random bytes and storing them encrypted with a Keystore-backed key:

Check the SQLCipher library's current artifact and class names, and measure the performance impact on your queries.

Practices

  • Use authenticated encryption (AES-GCM / AEAD), never ECB or unauthenticated modes.
  • Never hard-code keys, and never derive keys from constants in the APK.
  • Exclude encrypted data and keysets from backups, since Keystore keys don't restore.
  • Handle key loss: treat undecryptable data as missing, and re-sync or sign out.
  • Encrypt only what needs it, because encryption costs CPU and complexity.

Examples

Health diary

Room with SQLCipher, biometric lock on open, and no cloud backup of the database.

Document wallet

PDFs encrypted with Tink streaming AEAD, plus FLAG_SECURE on the viewer.

Banking session

Tokens via Tink AEAD in DataStore, cleared on logout.

Frequently asked questions

Is device encryption enough?

For low-sensitivity data, usually yes. For secrets and regulated data, app-level encryption adds protection for backups and some compromised-device scenarios.

Does encryption slow my app?

Some, especially for large files or databases. Measure, and encrypt selectively.

Can I use the deprecated library a bit longer?

Existing code continues to function, but it won't get updates. Plan migration rather than adding new usage.

Conclusion

Encrypt sensitive data at the app level with Keystore-protected keys: Tink AEAD for small values, streaming AEAD for files, and SQLCipher for databases. Migrate off the deprecated EncryptedSharedPreferences, exclude secrets from backup, and handle key loss gracefully.
