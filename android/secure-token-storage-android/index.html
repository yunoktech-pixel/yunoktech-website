🔌 APIs, Databases, and Backend Integration

Secure Token Storage and API Authentication

Access and refresh tokens are the keys to a user's account. Stored carelessly in plain SharedPreferences, logs or backups, they can be stolen and replayed. Here's a practical, current approach to storing tokens and handling API authentication on Android.

On Android, your app's private storage is sandboxed from other apps. That's a strong baseline. But tokens can still leak through device backups, rooted or compromised devices, debug logs, or analytics. Defence in depth means encrypting secrets with keys the app can't export, and limiting what a stolen token can do.

Threat model first

ThreatMitigation
Other apps reading your filesApp sandbox (default); never store tokens on shared storage
Tokens extracted from backupsExclude token files from backup; encrypt with non-exportable Keystore keys
Rooted device or malware with rootKeystore-backed encryption raises the bar; short-lived access tokens limit damage
Leaks via logs, crash reports, analyticsRedact Authorization headers; never log tokens
Stolen refresh tokenServer-side rotation and revocation; device binding where available

What about EncryptedSharedPreferences?

For years, Jetpack Security's EncryptedSharedPreferences was the standard answer. The androidx.security:security-crypto library has since been deprecated. It still works in existing apps, but new code should use an alternative, typically DataStore with Tink-based encryption and a Keystore-wrapped key, and existing apps should plan a migration.

Implementation: encrypted token store

AndroidX has also introduced a dedicated DataStore + Tink integration artifact. Check its status (it was alpha at the time of writing) before adopting it instead of a custom serializer. Initialise the cache at startup, for example by collecting tokens in an application scope, before the first authenticated request.

Exclude secrets from backup

Reference it with android:dataExtractionRules in the manifest, and provide equivalent fullBackupContent rules for Android 11 and lower. Keystore keys aren't backed up, so restored ciphertext would be undecryptable anyway, but excluding it avoids confusing states.

Token lifecycle best practices

  • Short-lived access tokens (minutes), plus a refresh token with server-side rotation: each refresh issues a new refresh token and invalidates the old one.
  • Refresh in one place: an OkHttp Authenticator. See OkHttp Interceptors.
  • Logout clears everything: tokens, cached user data, and a server-side revocation call.
  • Treat decryption failure as signed out. Keys can be invalidated, for example after some device security changes.

Variations

Banking-grade apps

Add Keystore keys requiring user authentication (biometric) for high-risk operations, plus Play Integrity checks on the server.

Firebase Auth

Firebase manages its own session storage. Request fresh ID tokens via the SDK rather than storing them yourself.

OAuth / OpenID Connect

Use AppAuth with PKCE in a Custom Tab for the login flow, then store the resulting tokens as above.

Common mistakes

  • Plain SharedPreferences or DataStore for tokens.
  • Hard-coded encryption keys in the APK, which aren't secret.
  • Logging tokens or full request headers.
  • Long-lived access tokens with no rotation.
  • Storing passwords on the device instead of tokens.

Frequently asked questions

Is the app sandbox not enough?

It protects against other apps on a healthy device. Encryption adds protection for backups, device transfers and some compromised-device scenarios.

Can a rooted device still steal tokens?

A sufficiently privileged attacker can read memory while the app runs. Encryption raises the cost, and short-lived tokens plus server-side checks limit the damage.

Should I store tokens in the Keystore directly?

The Keystore stores keys, not arbitrary data. Store encrypted tokens elsewhere, using a Keystore key for encryption.

Conclusion

Store tokens encrypted with a non-exportable Android Keystore key (for example DataStore plus Tink), exclude them from backups, keep access tokens short-lived with rotating refresh tokens, refresh in one place, and never log them. Migrate away from the deprecated EncryptedSharedPreferences.
