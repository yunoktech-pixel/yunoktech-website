🏛️ Android Architecture and Clean Code

Design Patterns Every Android Developer Should Know

You already use design patterns every day in Android, often without naming them: Flow is Observer, Retrofit.Builder is Builder, Hilt modules are Factories. Recognising patterns helps you read libraries faster, communicate designs, and choose solutions deliberately.

Design patterns are named, reusable solutions to recurring design problems. Kotlin removes the boilerplate many of them needed in Java, but the ideas remain essential, especially for reading codebases and discussing designs in reviews and interviews.

Patterns at a glance

PatternProblem it solvesWhere Android uses it
ObserverNotify many listeners of changesFlow, StateFlow, LiveData, Compose state
RepositoryHide data sources behind one APIData layer
BuilderConstruct complex objects step by stepRetrofit.Builder, NotificationCompat.Builder, Room.databaseBuilder
FactoryCentralise creation logicViewModelProvider.Factory, Hilt @Provides
SingletonOne shared instanceKotlin object, Hilt @Singleton
AdapterMake incompatible interfaces work togetherRecyclerView.Adapter, Retrofit CallAdapter, callback → suspend wrappers
DecoratorAdd behaviour by wrappingOkHttp interceptors, Compose Modifiers, by delegation
StrategySwap algorithms at runtimeSorting comparators, payment handlers, retry policies
FacadeSimple interface over a complex subsystemMedia3 player, your own SDK wrappers
StateBehaviour depends on stateSealed UiState with when, MVI reducers

Singleton: use with care

Kotlin's object makes singletons trivial, which makes them easy to overuse. Global singletons with state hurt testability. Prefer DI-scoped singletons (@Singleton in Hilt), which can be replaced in tests.

Choosing patterns

Many variants of behaviour

Strategy (with DI multibinding if the variants are pluggable).

Ugly third-party API

Facade or Adapter, so the rest of the app stays clean and the SDK is replaceable.

Cross-cutting behaviour

Decorator: logging, caching and auth headers without touching core logic.

Frequently asked questions

Are design patterns outdated in Kotlin?

Some implementations are simpler (builders, singletons, decorators), but the concepts remain useful vocabulary and design tools.

Is MVVM a design pattern?

It's an architectural pattern: a larger-scale structure built from smaller patterns such as Observer.

Which patterns come up in Android interviews?

Repository, Observer, Singleton (and its pitfalls), Factory, Builder, Adapter and Decorator, usually with an Android example.

Conclusion

Android code is full of design patterns: Observer in Flow, Builder in SDK setup, Decorator in interceptors and modifiers, Adapter around callbacks, Strategy for interchangeable behaviour, and Facade over complex SDKs. Use Kotlin features to implement them lightly, and name them to communicate clearly.
