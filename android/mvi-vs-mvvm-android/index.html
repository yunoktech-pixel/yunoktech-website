MVVM vs MVI: Which Android Architecture Should You Use?

MVVM and MVI both put a ViewModel between your UI and your data, and in Compose apps they look more alike than most blog posts admit. Here's exactly where they differ, the same screen in both styles, and how to choose.

Ask five Android developers whether they use MVVM or MVI and you'll get five definitions. Some teams call any app with a ViewModel "MVVM". Others call any app with a sealed class Intent "MVI". The arguments are often about naming, not engineering.

This article cuts through that. It's for intermediate developers who already know ViewModels and StateFlow and want to decide how to structure screen logic. You'll see the precise difference between the two patterns, the same feature implemented both ways, how each handles one-off events such as navigation and snackbars, and how they affect testing.

What MVVM and MVI actually mean on Android

MVVM (Model–View–ViewModel)

The View (Activity, Fragment or composable) observes state exposed by a ViewModel, and calls ViewModel functions in response to user actions. The Model is your data and business layer (repositories, use cases). In modern Android MVVM, the ViewModel usually exposes a single StateFlow<UiState> and public functions like onSearchChange(query) or retry().

MVI (Model–View–Intent)

MVI makes the flow even stricter. Every user action is an Intent (an object, not a function call; unrelated to Android's Intent class). All intents go through one entry point. State changes happen in a reducer, a pure function (oldState, result) -> newState. The View renders one immutable state object.

The honest overlap

Google's recommended architecture, a ViewModel exposing immutable UI state through StateFlow with events flowing up from the UI, is already unidirectional data flow. MVVM done this way is very close to MVI. The real difference is how strictly you formalise intents and state transitions.

The hard part: one-off events

Navigation, snackbars and toasts are the classic pain point in both patterns. If you store "navigate to product 42" in state, rotating the device may navigate again. If you use a hot SharedFlow without a buffer, events emitted while the UI isn't collecting are lost. Teams typically choose one of two approaches:

  • A buffered Channel exposed as a Flow, as in the examples above, collected with repeatOnLifecycle. Simple and widely used. In rare edge cases an event can still be dropped if it is delivered exactly as the collector is cancelled, so keep effects idempotent and non-critical.
  • Model the event as state and "consume" it. Store, for example, userMessage: String? in UI state and call onMessageShown() after displaying it. This is the approach Android's architecture guidance recommends, because state can't be lost.

Whichever you choose, choose it once for the whole codebase.

Testing: where MVI shines

Reducer tests are plain JUnit: no dispatchers, no fakes, no waiting. MVVM ViewModels are also very testable with runTest and a fake repository, but you test transitions through the async code rather than in isolation.

MVVM vs MVI at a glance

AspectMVVM (with UDF)MVI
User actionsPublic functionsSealed Intent objects, one entry point
State updatesAnywhere in the ViewModelOnly via a reducer
BoilerplateLowMedium–high (Intent, Result, Effect, State)
TraceabilityGoodExcellent: every transition is enumerable and loggable
Learning curveGentleSteeper; teams need shared conventions
Best forMost screens, CRUD apps, small and medium teamsComplex, highly interactive screens; large teams wanting strict consistency
RiskState logic gets scattered as screens growCeremony on simple screens; over-engineering

When to use which: real scenarios

Settings or profile screen

MVVM. A handful of actions and simple state. MVI's Intent/Result layers would add files without adding clarity.

Checkout, chat or editor

MVI. Many interacting events (payment status, validation, retries, real-time updates) where an explicit reducer prevents impossible state combinations.

Mixed codebase, many teams

MVVM with UDF rules as the baseline, and MVI-style reducers allowed for complex screens. Consistency of state exposure matters more than the label.

Common mistakes with both patterns

  • Multiple mutable state streams (isLoading, results, error as separate flows). They can disagree with each other. Prefer one immutable state object per screen.
  • Exposing MutableStateFlow publicly. The UI could then mutate state, which breaks unidirectional flow.
  • Side effects inside the reducer, such as network calls, logging or navigation. Reducers must be pure.
  • Passing Context or Views into the ViewModel, which leaks Activities across configuration changes.
  • Choosing MVI for the résumé rather than for the screen's complexity.

Frequently asked questions

Is MVI better than MVVM?

Neither is universally better. MVI gives stricter, more traceable state transitions at the cost of boilerplate. MVVM with a single immutable state is simpler and sufficient for most screens.

Does Google recommend MVVM or MVI?

Google's architecture guide doesn't mandate either name. It recommends state holders (usually ViewModels) exposing immutable UI state with unidirectional data flow. Both patterns can follow that guidance.

Do I need a library for MVI?

No. As shown above, Kotlin sealed types, StateFlow and a reducer function are enough. Libraries can add conventions and tooling, but also dependencies to maintain.

Can I mix MVVM and MVI in one app?

Yes, as long as the team agrees where each is used. A common approach is MVVM by default, with reducers for complex screens.

Where do use cases fit?

Use cases belong to an optional domain layer below the ViewModel. They are independent of whether the ViewModel follows MVVM or MVI. See Clean Architecture in Android.

Conclusion

MVVM and MVI aren't rival philosophies. They are two levels of strictness on the same unidirectional data flow. Start with MVVM and a single immutable UI state. Move to MVI's intents and reducers when a screen's state transitions get hard to reason about, and agree on one approach to one-off events across the whole team.

Next step: take one of your existing ViewModels and list every way its state can change. If the list is short, MVVM is serving you well. If it's long and scattered, extract a reducer. Then read Clean Architecture in Android: Practical Lessons to structure the layers beneath the ViewModel.
