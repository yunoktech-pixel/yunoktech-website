Kotlin vs Java for Android Development

Should you learn Kotlin or Java for Android, and if your app is already in Java, is it worth migrating? Here is a direct comparison with side-by-side code, the real trade-offs, and a clear recommendation for each situation.

"Kotlin or Java?" is still one of the first questions new Android developers ask, and teams with older apps ask a version of it too: is migrating worth the effort? The honest answer has changed over the years. In 2026 it depends less on the languages and more on where the Android ecosystem is heading.

This comparison is for beginners choosing a first language, Java developers moving to Android, and teams maintaining Java codebases. You'll see the practical differences in side-by-side code, where Java still matters, what interop looks like in a mixed codebase, and a recommendation for each situation.

The short answer

Recommendation

Learn Kotlin first for Android. Google announced a Kotlin-first approach to Android in 2019. New Jetpack APIs, Jetpack Compose, the official samples and most documentation assume Kotlin. Java remains fully supported for running and maintaining apps, and it is still worth being able to read, because many production codebases and libraries contain it.

That recommendation rests on concrete technical reasons, not fashion. The rest of this article explains them.

How Android got here

Android apps were originally written in Java, using a subset of the Java standard library and Android's own runtime (Dalvik, later ART). Kotlin, created by JetBrains, compiles to the same JVM bytecode, which Android's build tools then convert to DEX bytecode. That shared target is why Kotlin and Java can live in the same project, call each other, and ship in the same APK.

  • 2017: Google announced official Kotlin support for Android.
  • 2019: Google declared Android development "Kotlin-first".
  • Since then: Jetpack Compose (Kotlin-only), coroutine-based APIs across Jetpack, and Kotlin-specific extensions (KTX libraries) have become the default way to build Android apps.

Side-by-side: the differences you'll feel every day

1. Null safety

NullPointerException has historically been one of the most common causes of Android crashes. Kotlin builds nullability into the type system. A String can never be null, and a String? must be handled before use. The compiler enforces this.

Kotlin can't prevent every NPE. Values coming from Java code without nullability annotations are "platform types" whose nullability the compiler doesn't know. But in a Kotlin-heavy codebase, null-related crashes become much rarer and are easier to trace.

2. Data models

Modern Java has narrowed this gap with records. Kotlin's data classes still add copy(), default arguments and named parameters. These matter a lot for immutable UI state in ViewModels.

3. Asynchronous code

This is the biggest practical difference on Android. Kotlin coroutines let you write sequential-looking asynchronous code with built-in cancellation tied to lifecycles such as viewModelScope. Java has no language-level equivalent on Android, so Java code typically uses callbacks, executors, ListenableFuture or RxJava.

4. UI toolkit

Jetpack Compose is written for Kotlin. Composable functions rely on the Kotlin compiler plugin and on Kotlin language features such as trailing lambdas. You can't write Compose UI in Java. If you choose Java, you are choosing XML Views for your UI, which is still supported but is no longer where Google invests most of its new UI work.

5. Expressiveness

Extension functions, when expressions, sealed types, scope functions (let, apply), and collection operators make typical Android code shorter. Shorter isn't automatically better, but less boilerplate leaves less room for bugs to hide.

What about performance?

Because both languages compile to the same bytecode, runtime performance differences in real apps are usually negligible compared with architecture choices, I/O, rendering and memory use. A few things to know:

  • Some Kotlin features generate extra bytecode, such as default arguments, lambdas captured in non-inline functions, and companion objects. R8 optimises much of this in release builds.
  • inline functions remove lambda allocation overhead for higher-order functions such as map and filter.
  • The Kotlin standard library adds some size, which R8 shrinking reduces.

If an app is slow, the language is very rarely the reason. Profile before blaming Kotlin or Java. Our Android performance guide shows where the real bottlenecks usually are.

Watch out for platform types

When Kotlin calls a Java method that lacks @Nullable or @NonNull annotations, the return type is a platform type (shown as String! in the IDE). Kotlin lets you treat it as non-null, so if Java returns null you get an NPE at that point. Annotate your Java APIs, or treat their results as nullable in Kotlin.

Which should you choose? Three real scenarios

Beginner starting Android

Problem
Limited time; needs skills that match current jobs and docs.
Choice
Kotlin + Jetpack Compose.
Why
Matches the official learning material and modern job descriptions.
Trade-off
You'll need to learn to read Java later for older code. That's much easier than the reverse.

Experienced Java backend developer

Problem
Strong Java skills, new to Android.
Choice
Kotlin, using your Java knowledge as a bridge.
Why
The JVM concepts transfer directly; Kotlin syntax takes days to weeks, not months.
Trade-off
Coroutines need a genuine mental-model shift from threads and futures.

Team with a large Java app

Problem
Stable Java code; new features to build.
Choice
Write new code in Kotlin; migrate old files only when you touch them.
Why
Interop makes gradual adoption low-risk, with no "big rewrite".
Trade-off
Two languages in one codebase for a while; agree on conventions and nullability annotations.

Migrating from Java to Kotlin safely

  1. Add Kotlin to the build by applying the Kotlin Android Gradle plugin. Recent Android Studio templates include it by default.
  2. Start with new code and tests. Write new features and unit tests in Kotlin. Tests are low-risk and let the team learn.
  3. Annotate Java nullability first (@Nullable / @NonNull) on classes you'll call from Kotlin.
  4. Convert files you're already changing with Android Studio's Convert Java File to Kotlin File, then review the result by hand. The converter produces working but often non-idiomatic code, with things like overuse of !! and lateinit.
  5. Keep commits small: one conversion per commit, behaviour unchanged, tests passing. Then make idiomatic improvements in a follow-up commit.

Common mistakes when switching to Kotlin

  • Writing "Java in Kotlin syntax": mutable vars everywhere, getters and setters, utility classes instead of extension functions.
  • Sprinkling !! to silence the compiler. Each one is a potential crash; model nullability properly instead.
  • Overusing scope functions: nested let/apply/also chains hurt readability. A plain if is often clearer.
  • Using GlobalScope for coroutines. It isn't tied to any lifecycle, so the work can leak. Use viewModelScope or lifecycleScope.

Frequently asked questions

Is Java dead for Android?

No. Java is supported, the Android framework itself contains a great deal of Java, and many apps and libraries are written in it. But new Android APIs and tooling are designed Kotlin-first, so Java is no longer the best choice for new app code.

Do I need to learn Java before Kotlin?

No. Kotlin is a complete language on its own. Being able to read Java helps when you work with older code or Java-only libraries, and Kotlin developers usually pick that up naturally.

Is Kotlin slower than Java on Android?

Not in any way that matters for typical apps. Both compile to DEX bytecode, and R8 optimises release builds. Architecture, I/O and rendering have far more impact on performance than the language.

Can I use Jetpack Compose with Java?

No. Compose relies on the Kotlin compiler plugin and Kotlin language features. A Java Activity can host Compose content written in Kotlin, but the composables themselves must be Kotlin.

Will knowing Kotlin help outside Android?

Yes. Kotlin is used for backend development (for example with Spring or Ktor) and for sharing code across platforms with Kotlin Multiplatform.

Conclusion

For Android in 2026, Kotlin is the default and Java is the legacy you should be able to read. Kotlin gives you compile-time null safety, coroutines for asynchronous work, and access to Jetpack Compose, and it interoperates with Java so smoothly that no existing project needs a risky rewrite.
