🧪 Testing, Debugging, and Performance

Debugging Crashes with Logcat

When an Android app crashes, Logcat holds the answer, usually in the first few lines of a stack trace. This guide teaches you to find the right lines quickly, interpret common exceptions, and turn a crash into a fix and a test.

"The app stopped" tells the user nothing and you even less. Logcat, Android's system log, records exactly which exception was thrown, where, and why. Learning to read it is one of the highest-leverage debugging skills you can build.

Common exceptions and their usual fixes

SecurityExceptionMissing runtime permissionRequest permission; check before use
TransactionTooLargeExceptionLarge Bundle (saved state, intent extras)Pass IDs; persist large data elsewhere

From crash to fix: using the debugger

  1. Click the file link in the stack trace (for example CartMapper.kt:18) to jump to the line.
  2. Set a breakpoint there, or an exception breakpoint for that exception type (Run → View Breakpoints).
  3. Run in debug and reproduce. Inspect variables and the call stack when it stops.
  4. Write a unit test that reproduces the failing input, fix the code, and watch the test pass.

Logging well

  • Use levels meaningfully: d for debug detail, i for milestones, w for recoverable problems, e for failures.
  • Never log tokens, passwords or personal data.
  • Strip verbose logs from release builds (for example with a logging wrapper or Timber's debug tree).

Crashes in production

Logcat only shows your device. For users' crashes, use Android vitals in the Play Console and a crash reporter such as Firebase Crashlytics. Upload R8 mapping files so stack traces are readable (see R8), and add breadcrumbs and custom keys (screen name, feature flag) to reproduce context.

Debugging scenarios

Crash only in release

Usually R8 or reflection. Reproduce with a minified build and add a targeted keep rule.

Crash after returning from background

Usually process death and a missing lateinit or state. Test with "Don't keep activities".

Crash on one manufacturer

Check Android version, permissions behaviour and WebView or OEM differences in vitals breakdowns.

Frequently asked questions

Logcat is too noisy. What can I do?

Filter by package:mine and level, create saved filters, and use consistent tags.

Why don't I see my logs?

Check the selected device and process, the filter, and that your logging isn't stripped in that build variant.

Can AI help read stack traces?

Yes. Tools like Gemini in Android Studio can explain traces and suggest causes, but verify suggestions against the code. See Debugging with AI.

Conclusion

To debug a crash: filter Logcat, read the exception and message, jump to the first frame in your code, check "Caused by", reproduce with breakpoints, and lock in the fix with a regression test. Use Android vitals and Crashlytics for production crashes.
