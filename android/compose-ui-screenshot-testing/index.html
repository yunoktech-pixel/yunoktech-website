Compose UI Testing and Screenshot Testing

Functional UI tests check that a screen behaves correctly. Screenshot tests check that it still looks correct. Compose makes both practical. This guide covers semantics-based UI tests and screenshot testing, and shows how to structure screens so tests stay simple.

A refactor changes padding in a shared component, and twenty screens shift by 8dp. A colour token is renamed, and the error state becomes unreadable in dark mode. Unit tests won't catch either. UI tests catch broken behaviour, and screenshot tests catch broken visuals.

Where UI and screenshot tests fit

Make screens testable first

Split each screen into a Route (connects to the ViewModel) and a stateless Screen (renders a UiState and emits events). Tests and previews then drive the Screen directly with any state. See State Hoisting.

Compose UI tests

  • Finders (onNodeWithText, onNodeWithContentDescription, onNodeWithTag) query the semantics tree, the same information accessibility services use. Good semantics make tests easier too.
  • Use Modifier.testTag("…") only when no user-visible text or description identifies a node.
  • Compose tests synchronise with the UI automatically, waiting for recomposition and animations to idle. For async work, use waitUntil { }.

More patterns: UI Testing in Jetpack Compose.

Screenshot testing

A screenshot test renders a composable, saves a reference image, and on later runs compares the new rendering against it, failing on visual differences.

Previews as screenshot tests

With Google's tool, previews placed in the screenshot test source set become tests. A multi-preview annotation makes each component render in several configurations:

You then run a Gradle task to update reference images and another to validate against them. The exact task names depend on the plugin version and whether you use the newer test-suite setup, so follow the current documentation.

Running in CI

  1. Commit reference images to the repository (or Git LFS).
  2. Run validation on every pull request, and publish the diff report as a CI artifact.
  3. When a change is intentional, regenerate references in the same PR so reviewers see the visual diff.
  4. Pin fonts, locale and rendering settings so images are deterministic.

What to screenshot

Design-system components

Buttons, cards and inputs in every state (enabled, disabled, error, loading), in light and dark, at large font scale.

Key screens

Empty, loading, error and populated states of high-traffic screens.

Localisation

Long-text languages and RTL layouts, where truncation and alignment bugs hide.

Common mistakes

  • Screenshotting screens that load live data or show the current time. Inject fixed data and clocks.
  • Hundreds of near-duplicate screenshots that nobody reviews.
  • Using test tags everywhere instead of improving semantics.
  • Blindly accepting regenerated references without looking at diffs.

Frequently asked questions

Do Compose UI tests need a device?

Instrumented tests run on a device or emulator. Compose UI tests can also run on the JVM with Robolectric for faster feedback.

Are screenshot tests flaky?

JVM-rendered screenshots are generally stable when inputs are deterministic. Device-based screenshots can vary with GPU and OS differences, so use tolerances.

Should I replace UI tests with screenshot tests?

No. They complement each other: screenshots verify appearance, and UI tests verify behaviour and interaction.

Conclusion

Structure screens as stateless, previewable composables, then use semantics-based UI tests for behaviour and screenshot tests for appearance across states, themes and font sizes. Run both in CI, and review visual diffs like code.
