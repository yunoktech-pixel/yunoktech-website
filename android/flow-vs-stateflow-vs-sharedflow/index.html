Flow vs StateFlow vs SharedFlow

Flow, StateFlow and SharedFlow look similar and are often used interchangeably, which causes lost events, duplicate network calls and screens that don't update. Here's the precise difference and a simple rule for choosing.

Two collectors of the same Flow trigger two network requests. A snackbar event fires while the screen is rotating and disappears. A StateFlow doesn't emit after you "update" a list. Each of these comes from choosing the wrong kind of flow, or misunderstanding how it behaves.

The one-table summary

Flow: the cold default for data sources

A cold flow does nothing until collected, and each collector gets its own run. That's ideal for repositories: the caller decides when and how long to observe.

StateFlow: state holders for the UI

StateFlow uses equality

If you mutate a list inside the current value and set it again, StateFlow sees an equal object and emits nothing. Always emit a new immutable value, for example _state.update { it.copy(items = it.items + item) }.

SharingStarted.WhileSubscribed(5_000) stops the upstream five seconds after the last collector leaves. That survives rotation without restarting, but stops work when the user truly leaves the screen.

SharedFlow: broadcasts

Key configuration: replay (how many past values new collectors receive), extraBufferCapacity and onBufferOverflow. With the default replay = 0, events emitted while nobody is collecting are lost. That's correct for some broadcasts, and wrong for one-off UI events.

One-off UI events: which tool?

Navigation and snackbars are where these choices bite. The options:

  • Model the event as state (recommended by Android's architecture guidance): store userMessage: String? in UI state and clear it after showing. Nothing can be lost.
  • Channel + receiveAsFlow(): buffers events until a single collector receives them. Each event is delivered to one collector.
  • SharedFlow with replay 0: events emitted during rotation, when nobody is collecting, are dropped. Generally avoid it for UI events.

Decision rule

  1. Exposing data from a repository or data source? Return a cold Flow.
  2. Exposing state to the UI? Use a StateFlow (via stateIn or MutableStateFlow).
  3. Broadcasting to several independent listeners, where missed values are acceptable or handled by replay? Use a SharedFlow.
  4. One-off UI event? Prefer state. Otherwise use a buffered Channel collected with repeatOnLifecycle.

Common mistakes

  • Exposing a cold flow from a ViewModel and collecting it from several composables, which restarts work on each collection and on every rotation.
  • Using stateIn(..., SharingStarted.Eagerly, ...) everywhere, which keeps upstreams running even when no UI is visible.
  • Calling stateIn inside a function that's called repeatedly, creating a new StateFlow each time. Create it once, as a property.
  • Using SharedFlow with no replay for navigation events.

Frequently asked questions

Is StateFlow a replacement for LiveData?

For new Kotlin code, generally yes. Collect it with collectAsStateWithLifecycle() or repeatOnLifecycle to get LiveData's lifecycle awareness.

Is StateFlow just a SharedFlow with replay 1?

Close: it behaves like a SharedFlow with replay 1, a required initial value, conflation and equality-based de-duplication. It also exposes a synchronous .value.

How do I test these?

Use runTest and collect into a list in backgroundScope, or use a library such as Turbine. See Testing ViewModels with Coroutines and Flow.

Conclusion

Flow is a cold recipe for data. StateFlow is hot, always holds the latest value, and is the right tool for UI state. SharedFlow is a configurable broadcast. Expose cold flows from repositories, convert them to StateFlow in ViewModels with stateIn, and model one-off UI events as state whenever you can.
