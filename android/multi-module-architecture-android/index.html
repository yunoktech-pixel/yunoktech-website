Multi-Module Architecture in Android: Pros, Cons, and Lessons

Splitting an Android app into Gradle modules can speed up builds, enforce architecture and let teams work independently. It can also create slow syncs, circular-dependency headaches and boilerplate. Here are the real pros, the real costs, and the lessons that decide whether modularization pays off.

A single :app module is the right start for almost every project. As the app grows to dozens of screens and several developers, one module means every change recompiles everything, any class can depend on any other, and ownership is blurry. Modularization addresses those problems, at a price.

What modules give you

Benefits

  • Build speed: unchanged modules come from the cache, and builds can parallelise
  • Enforced boundaries: the compiler blocks forbidden dependencies
  • Encapsulation: internal hides implementation details
  • Ownership: teams own modules
  • Reuse: shared design system and core modules
  • Dynamic delivery: optional on-demand feature modules

Costs

  • More Gradle configuration to maintain
  • Slower Gradle sync with many modules
  • Cross-feature navigation needs indirection
  • Visibility decisions (api vs implementation, internal)
  • Over-modularization makes simple changes touch many modules

A typical structure

api vs implementation

Prefer implementation. It keeps dependencies from leaking to consumers and limits recompilation when they change. Use api only when a dependency's types appear in your module's public signatures.

Convention plugins: avoid copy-pasted build files

Each new feature module then needs only a few lines. Google's Now in Android sample uses this approach.

Navigating between features without coupling

If :feature:home needs to open search, it shouldn't depend on :feature:search. Common approaches:

  • Route keys in a shared module (:core:navigation), with each feature providing its entries, and :app assembling the graph.
  • Lambdas passed from :app: HomeScreen(onOpenSearch = { backStack.add(Search) }).

Lessons learned

Modularize for a reason

Measure build times or identify ownership pain first. "Clean architecture says so" isn't enough.

Start with core extraction

Moving the design system, network and database into modules usually brings the biggest early gains.

Watch the graph

Visualise dependencies regularly. A "core:common" module that everything depends on becomes a bottleneck.

Granularity is a trade-off

Too few modules give little benefit. Too many give slow syncs and ceremony. Feature-sized modules are a good default.

When it pays off

SituationRecommendation
Solo developer, small appSingle module with clear packages
Growing app, slow incremental buildsExtract core modules, then the largest features
Several teamsFeature modules with owners; convention plugins; dependency rules in CI
Planning KMPPure-Kotlin domain and data modules that can become multiplatform

Frequently asked questions

Does modularization always make builds faster?

Incremental builds and CI with caching usually improve, but configuration and sync times can grow with the number of modules. Measure before and after.

Should each layer be its own module?

Not necessarily. Many teams split by feature first, and add layer modules (domain, data) where boundaries need enforcing.

How do I wire DI across modules?

Each module contributes Hilt modules installed in components, and the app module brings them together automatically through Hilt's aggregation.

Conclusion

Multi-module architecture trades build configuration effort for faster incremental builds, enforced boundaries and team ownership. Start simple, extract core modules first, use implementation by default and convention plugins for consistency, and never let features depend on each other.
