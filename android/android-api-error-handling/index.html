Handling API Errors and Network Failures

Users on trains, lifts and patchy 4G will hit every failure path your app has. Good error handling turns those moments into clear messages and automatic recovery instead of spinners that never stop. Here's a complete, layered approach.

"Something went wrong" is the least helpful message an app can show. Was the user offline? Did their session expire? Is the server down? Did they enter invalid data? Each case needs a different message and a different recovery. The fix is to classify errors at the boundary and carry that meaning up to the UI.

Applying it in the repository

Mapping errors to UI

Validation errors map to field-level messages in form state. Unauthorized triggers a sign-out flow. Offline shows an inline banner while cached content stays visible.

Observing connectivity

Use this to show an offline banner and trigger retries when connectivity returns. A network can still be unusable (captive portals, server outages), so always handle request failures too.

Retry policy

  • Retry automatically: I/O errors and 5xx on idempotent requests (GET, PUT with the same body), with exponential backoff and jitter, limited attempts.
  • Respect 429 (Too Many Requests) and any Retry-After header.
  • Never auto-retry validation errors or non-idempotent POSTs without idempotency keys.
  • Queue writes that must eventually succeed with WorkManager.

UX patterns

List screen offline

Keep showing cached items with an "Offline: showing saved data" banner, and refresh automatically when back online.

Form submission fails

Keep the user's input, highlight invalid fields, and offer retry. Never clear the form on error.

Session expired

Try a silent token refresh. If that fails, explain and take the user to sign-in, returning them afterwards.

Monitoring

Log unexpected and parsing errors to your crash or analytics tool (without personal data), and track error rates per endpoint. Spikes after a release often reveal API contract changes.

Frequently asked questions

Should repositories return Result instead of throwing?

Both are valid. Throwing a typed AppException keeps signatures simple, and Result or sealed types make failures explicit. Choose one convention for the codebase.

Is checking connectivity before each request useful?

Not as a gate: networks can report "available" and still fail. Use connectivity for UX hints and retries, and always handle actual request errors.

How do I test error handling?

Use MockWebServer to return error codes and malformed bodies, and fakes that throw IOException, then assert on the resulting UI state.

Conclusion

Classify failures at the data boundary into typed errors, map them to specific messages and recoveries in the UI, retry only what's safe, keep cached content visible offline, and monitor what slips through.
