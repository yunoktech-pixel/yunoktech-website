🚀 App Publishing, Monetization, and Product Development

How to Prepare an Android App for Production

'It works on my phone' is not a release criterion. Production readiness covers build configuration, observability, performance, accessibility, security, privacy, and a plan for when things go wrong. Use this checklist before your first release and every major one after.

The first week after launch is when you learn what you didn't test: the crash on a specific manufacturer, the login loop after a password change, the screen that breaks in Hindi. Preparing for production means reducing those surprises and making the remaining ones visible and recoverable.

Readiness areas

Build configuration

  • ☐ Correct applicationId, versionCode (always increasing) and versionName
  • ☐ targetSdk meets the current Play requirement; behaviour changes tested
  • ☐ R8 and resource shrinking enabled; minified build tested end to end
  • ☐ Release build is not debuggable; debug-only tools (LeakCanary, StrictMode) excluded
  • ☐ Production API endpoints and config; feature flags have safe defaults

Observability

  • ☐ Crash reporting (for example Crashlytics) with R8 mapping files uploaded
  • ☐ Analytics for key funnels, with privacy-respecting events. See Analytics and Crash Reporting
  • ☐ Non-fatal error logging for important failures (payments, sync)
  • ☐ Android vitals reviewed, with alerts configured

Performance

  • ☐ Cold start measured on a mid-range device; Baseline Profile included
  • ☐ No StrictMode violations on main flows; no jank in key lists
  • ☐ App size checked with APK Analyzer

Quality and accessibility

  • ☐ Loading, empty, error and offline states on every data screen
  • ☐ Rotation, dark mode, large font, small and large screens checked
  • ☐ TalkBack pass on key flows; content descriptions; touch targets
  • ☐ Play Console pre-launch report reviewed

Security and privacy

  • ☐ No secrets in the APK; release logging scrubbed
  • ☐ Exported components audited; TLS only
  • ☐ Privacy policy published; Data safety form accurate, including SDKs
  • ☐ Account deletion available if users can create accounts

Localisation

  • ☐ All user-facing strings in resources; translations reviewed by native speakers
  • ☐ Long-text languages and RTL layouts checked; numbers, dates and currency formatted per locale

Rollout and recovery

  1. Release to internal, then closed testing, then a staged production rollout.
  2. Define halt criteria: for example, a crash-free user rate dropping below your baseline.
  3. Be able to disable features remotely (feature flags or remote config).
  4. Have an in-app update prompt strategy for critical fixes.
  5. Prepare support channels and review responses.

Right-size it

Side project

Build config, crash reporting, basic accessibility, privacy policy, staged rollout.

Startup MVP

Add analytics funnels, feature flags and performance baselines.

Enterprise or fintech

All of the above, plus security testing, compliance reviews and formal incident response.

Frequently asked questions

What's a good crash-free rate target?

Aim as high as you can, and watch Google Play's bad-behaviour thresholds for crash and ANR rates in Android vitals. Track the trend per release.

Should I use in-app updates?

Play's in-app updates API lets you prompt users to update, which is useful for critical fixes. Use flexible updates for most cases and immediate updates sparingly.

Do I need a staging backend?

Strongly recommended, so testers and CI don't touch production data.

Conclusion

Production readiness is a checklist across build, observability, performance, quality, security, privacy, localisation and rollout. Run it before every major release, and you'll spend launch week improving the app instead of firefighting.
