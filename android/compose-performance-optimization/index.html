Compose Performance Optimization

Compose is fast when you work with its model and slow when you fight it. This guide shows how to measure, find unnecessary recomposition, fix stability issues, defer state reads to cheaper phases, and tune lazy lists, in order of impact.

"Compose is slow" usually means one of a few specific problems: testing a debug build, recomposing a large tree on every scroll frame, or doing expensive work inside composables. All of them are measurable and fixable.

Step 0: Measure correctly

  • Use a release-like build (minified, non-debuggable). Debug Compose is significantly slower.
  • Add a Baseline Profile. Compose ships its own profile rules, and your app's critical journeys benefit from one too. See Baseline Profiles.
  • Use Macrobenchmark with FrameTimingMetric for scrolling and animation jank.
  • Use Layout Inspector's recomposition counts to see which composables recompose and how often.

Understand the three phases

The fixes, in order of impact

1. Defer reads of fast-changing state

2. Use derivedStateOf when outputs change less than inputs

3. Don't do expensive work in composition

4. Tune lazy lists

  • Provide key and contentType for every items call.
  • Keep item composables small and parameters simple (IDs, strings, immutable UI models).
  • Size images to their display size, and avoid decoding full-resolution bitmaps.

5. Stability and strong skipping

Compose skips a composable when its parameters are equal to last time and considered stable. With strong skipping mode, the default in recent Compose compiler versions, composables with unstable parameters can still be skipped, using instance equality for those parameters, and lambdas are remembered automatically. This removed many earlier stability headaches, but a few things still matter:

Use the Compose compiler's stability reports to see which classes are unstable. Fix the ones that appear on hot paths, not all of them.

6. Narrow recomposition scope

Passing a () -> Float provider instead of the value lets only ProgressBar react to every progress tick.

Tools checklist

Is scrolling janky?Macrobenchmark FrameTimingMetric, Perfetto trace
What recomposes too often?Layout Inspector recomposition counts and highlighting
Which classes are unstable?Compose compiler stability reports
Is startup slow?Macrobenchmark StartupTimingMetric, Baseline Profile comparison

Typical fixes in the wild

Feed jank

Missing keys, large images and formatting in item bodies. Fixed with keys, sized images and preformatted UI models.

Collapsing toolbar stutter

Scroll offset read in composition. Fixed with lambda offset and graphicsLayer.

Whole screen recomposes per keystroke

Text state hoisted too high and read at the root. Fixed by narrowing reads to the field and the components that need them.

Common mistakes

  • Optimising stability everywhere before measuring.
  • Backwards writes: writing state that was already read in the same composition, which triggers recomposition loops.
  • Using derivedStateOf for cheap derivations that change as often as their inputs.
  • Testing on a debug build and concluding Compose is slow.

Frequently asked questions

Is recomposition itself bad?

No. It's how Compose works. Excessive recomposition of large subtrees on every frame is the problem.

Do I need @Stable and @Immutable everywhere?

No. With strong skipping and immutable data classes, most code needs no annotations. Use them deliberately where reports show a hot-path problem.

How much do Baseline Profiles help Compose?

They often noticeably improve startup and first-scroll smoothness because Compose code is large. Measure the gain with Macrobenchmark in your own app.

Conclusion

Fast Compose comes from measuring release builds, reading fast-changing state late, keeping composition cheap, tuning lazy lists and fixing stability where it matters. Baseline Profiles and Macrobenchmark prove the improvement.
