Migrating Legacy Android Apps to Modern Architecture

Legacy apps still earn money, so you can't stop and rewrite. The safest path is incremental: wrap, extract and replace piece by piece, shipping every step. Here's a migration plan that works on real codebases.

Refactoring Legacy Apps covers safe, local refactoring techniques. This article is the bigger picture: a sequenced migration from a legacy stack to modern Android architecture, without a rewrite.

From where to where

LegacyModern target
JavaKotlin (new code first)
Logic in Activities/FragmentsViewModels + repositories (+ use cases where useful)
AsyncTask, callbacks, RxJavaCoroutines and Flow
Singletons, manual wiringHilt
XML layouts, findViewByIdCompose (screen by screen)
SQLiteOpenHelperRoom
SharedPreferencesDataStore
Single moduleModules by feature/layer when size justifies

The strangler approach

The migration sequence

  1. Foundations: update Gradle, AGP and dependencies; enable Kotlin; add crash reporting and CI with tests. See CI/CD.
  2. Safety net: characterization tests around critical flows (login, checkout), plus a few UI smoke tests.
  3. Data layer first: introduce repositories that wrap existing data code, so screens stop talking to databases and network directly.
  4. ViewModels: move screen logic out of Activities/Fragments, starting with the most-changed screens.
  5. Async: replace AsyncTask/callbacks with coroutines at the repository boundary.
  6. DI: add Hilt and migrate singletons gradually.
  7. UI: new screens in Compose; migrate existing screens when they need significant changes.
  8. Storage: Room and DataStore migrations with data-migration tests.

Compose interop during migration

Keep the Fragment and navigation for now, and replace the UI inside. Migrate navigation later. See XML to Compose with AI.

Measure progress meaningfully

  • Crash-free rate and ANR rate in migrated areas.
  • Lead time for changes in migrated vs legacy features.
  • Test coverage on critical flows.
  • Avoid vanity metrics like "% Kotlin files" as the main goal.

Pitfalls

Big-bang rewrite

Months without shipping, feature parity gaps, new bugs. Usually avoid.

Mixing refactors with features

Hard to review and roll back. Keep them separate.

Two patterns forever

Set a direction and a rule ("touched screens get migrated") so migration finishes.

Frequently asked questions

When is a rewrite justified?

Rarely: when the platform or product fundamentally changes, or the codebase is small. Even then, consider rewriting module by module.

Can AI speed up migration?

Yes, for explaining code, drafting conversions and tests. Verify carefully. See AI for Legacy Java.

Conclusion

Migrate incrementally: foundations and tests first, then repositories, ViewModels, coroutines, Hilt, Compose and modern storage, shipping every step and measuring outcomes that matter.
