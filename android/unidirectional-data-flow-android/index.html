Unidirectional Data Flow in Android

Unidirectional data flow is the principle underneath MVVM, MVI and Compose state hoisting: state flows one way, events flow the other, and each piece of data has exactly one owner. Understand UDF once and every Android architecture pattern makes more sense.

In a bidirectional design, a text field updates a variable, the variable updates a label, the label's listener updates another variable... and nobody can say which value is "correct" when they disagree. Unidirectional data flow (UDF) removes that ambiguity with one rule: state flows down, events flow up.

The rule

  • State is owned by a single source of truth and flows down to consumers, which can only read it.
  • Events (user actions, system callbacks) flow up to the owner, which decides how state changes.
  • The owner produces a new immutable state, which flows down again.

UDF end to end

Even the optimistic update goes through the database, so every screen showing this post agrees.

Benefits

  • Consistency: one owner per piece of data means no conflicting copies.
  • Predictability: state changes happen in known places, so bugs are easier to trace.
  • Testability: feed events in, assert state out.
  • Survives configuration changes, because state lives in ViewModels and repositories rather than Views.

Common UDF violations

ViolationSymptomFix
UI mutates shared state directly (public MutableStateFlow)State changes from unexpected placesExpose read-only StateFlow; mutate via ViewModel functions
Local copy of ViewModel state in a composableUI and ViewModel disagreeRead directly from state; hoist instead of copying
Two ViewModels both caching the same dataScreens show different valuesMove the truth to the data layer and observe it
Child components calling repositoriesHidden data flows, hard testsEvents up to the screen's ViewModel

UDF at different scales

Component level

State hoisting: value plus onValueChange. See State Hoisting.

Screen level

ViewModel exposes UiState, and the screen calls functions. See ViewModel and StateFlow.

App level

The database as source of truth, with network sync writing into it. See Offline-First.

Frequently asked questions

Is UDF the same as MVI?

MVI is a strict form of UDF that formalises events as intents and changes as a reducer. MVVM with a single immutable state is also UDF.

Doesn't UDF add latency for text input?

Not noticeably when state updates are synchronous on the main thread, as with MutableStateFlow.update or Compose state. Avoid asynchronous round-trips for every keystroke.

Where do one-off events fit?

Model them as state that the UI consumes and clears, so they still follow the unidirectional loop.

Conclusion

UDF is a simple discipline: one owner per piece of state, state down as immutable values, events up as function calls. Apply it at component, screen and app level and your Android code becomes predictable, consistent and testable.
