Analytics and Crash Reporting for Android Apps

Without analytics you don't know whether users reach your key feature. Without crash reporting you only learn about crashes from one-star reviews. Here's how to instrument an Android app so you get actionable data, while respecting privacy.

Many apps track either everything (thousands of meaningless events) or nothing. Good instrumentation starts from questions: where do new users drop off, which features drive retention, which crashes affect most users, and adds just enough events to answer them.

The observability stack

Designing analytics events

  1. Write the questions first: "What % of new users create their first note within a day?"
  2. Define a small event set: verbs in snake_case, with consistent parameters.
  3. Document it in a tracking plan, and review new events in PRs.

A typed wrapper prevents typos, makes events searchable in code, and lets you swap providers, or use a no-op in tests and debug builds.

Crash reporting that helps you fix things

  • Upload R8 mapping files so stack traces are readable. The Crashlytics Gradle plugin can do this.
  • Triage by users affected and trend after release, not just event counts.
  • Use Android Studio's App Quality Insights to jump from crash clusters to source.

Privacy and consent

  • Never log personal data (names, emails, phone numbers, message content) in events or crash logs.
  • Respect consent requirements in your markets, and provide an opt-out (for example setAnalyticsCollectionEnabled(false)).
  • Disclose analytics and crash SDKs in the Play Data safety form and privacy policy.
  • Disable collection in debug builds to keep data clean.

From data to decisions

Onboarding drop-off

The funnel shows 40% drop at a permission screen. Move the permission request into context, then measure again.

Crash after release

A new cluster on one Android version. Halt the staged rollout, fix it, and resume.

Feature value

Users who use search in week 1 retain better. Make search more discoverable.

Frequently asked questions

How many events should I track?

Usually a few dozen well-defined events are enough. Each event should answer a question someone will actually ask.

Crashlytics or Android vitals?

Both. Vitals shows system-level data for all Play users, including ANRs. Crashlytics adds custom context, non-fatals and faster iteration.

Can analytics slow my app?

SDK initialisation and heavy logging can affect startup. Initialise lazily where possible, and measure.

Conclusion

Instrument with intent: a small, documented event set for product questions, crash reporting with context and non-fatals for engineering, Android vitals for system health, and privacy by design throughout.
