Firebase Cloud Messaging and Push Notifications

Push notifications bring users back to your app, when they're relevant. This guide sets up Firebase Cloud Messaging end to end: runtime permission, tokens, message types, channels, deep links, sending from a server with the HTTP v1 API, and testing.

Notifications are a privilege, not a channel you own. Since Android 13, users must explicitly grant permission, and they revoke it quickly when apps spam. This guide shows how to implement FCM correctly and how to ask for permission at a moment that makes sense.

How FCM delivery works

Setup

Ask for permission at the right moment

On Android 13 (API 33) and later, POST_NOTIFICATIONS is a runtime permission. Ask in context, for example after the user places an order ("Get delivery updates?"), not on first launch.

Notification channels

Users can turn off "Offers" while keeping "Order updates". Separate channels respect their choice and keep important alerts alive.

Handling tokens and messages

Notification vs data messages

Notification messageData message
App in backgroundSystem shows it automaticallyDelivered to onMessageReceived
App in foregroundonMessageReceivedonMessageReceived
Control over displayLimitedFull (channels, actions, grouping)
Best forSimple marketing or announcementsTransactional alerts, deep links, silent sync

Sending from your server (HTTP v1)

The legacy FCM server APIs have been retired. Use HTTP v1 with OAuth 2.0 service-account credentials, which must stay on your server and never ship in the app. The Firebase Admin SDK handles authentication for you.

Testing

  • Use the Firebase console's "Send test message" with your device token.
  • Test foreground, background and killed states. They behave differently.
  • Test with notifications disabled, and with a specific channel disabled.
  • Check behaviour on manufacturers with aggressive battery management.

Good notification use cases

Transactional

Order shipped, payment received, OTP alternatives. High value, expected by users.

Collaboration

Mentions, replies and shared-document changes, grouped and rate-limited.

Silent sync

A data message triggers WorkManager to refresh content before the user opens the app.

Common mistakes

  • Requesting notification permission on first launch with no context.
  • Sending everything through one channel, so users disable all notifications.
  • Heavy work in onMessageReceived. Enqueue WorkManager instead.
  • Putting personal or sensitive data in notification text on the lock screen.
  • Not handling token refresh, so pushes silently stop reaching users.

Frequently asked questions

Why don't my notifications arrive on some phones?

Common causes are denied permission, a disabled channel, aggressive OEM battery optimisation for background apps, or an invalid token on the server. Check delivery reports in Firebase.

Can I send to groups of users?

Yes, with topics (subscribeToTopic) or by sending to multiple tokens from your server.

Is FCM free?

FCM itself is free to use. Your backend infrastructure for sending messages has its own costs.

Conclusion

A solid FCM integration asks for permission in context, uses meaningful channels, prefers data messages for transactional alerts with deep links, keeps tokens in sync with your server, and sends with the HTTP v1 API from secure server code.
