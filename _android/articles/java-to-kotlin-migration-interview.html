"How would you migrate our 300k-line Java app to Kotlin?" is a common senior question. The best answers show you understand interop deeply, migrate incrementally with safety nets, and focus effort where it delivers value.

Interop questions

What are platform types?

Types from Java without nullability information (shown as String!). Kotlin lets you treat them as nullable or non-null, and a wrong assumption causes an NPE at runtime. Fix it with @Nullable/@NonNull annotations on the Java side.

How do you make Kotlin APIs pleasant to call from Java?

class Prices { companion object { @JvmStatic fun format(amount: Double): String = "₹%.2f".format(amount) // Prices.format(...) in Java const val CURRENCY = "INR" // a true Java constant } } @JvmOverloads fun toast(context: Context, text: String, long: Boolean = false) { /* ... */ } // overloads for Java // In a separate file, as its very first line (before the package statement): // @file:JvmName("StringUtils") → top-level functions appear as StringUtils.xxx() in Java

How do Kotlin properties appear in Java?

As getters and setters (getName()/setName()), with isX() for properties starting with "is". Use @JvmField to expose a field directly.

Checked exceptions?

Kotlin has none. If Java callers must catch an exception, declare it with @Throws(IOException::class).

Suspend functions from Java?

They're awkward (an extra Continuation parameter). Provide Java-friendly wrappers, such as callbacks or futures, at the boundary.

Strategy questions

How would you prioritise what to convert?

Convert files you're actively changing, plus high-value areas such as frequently changed features, crash hotspots and code that would benefit from coroutines or Compose. Leave stable, rarely touched Java alone until there's a reason.

How do you keep behaviour unchanged?

Write characterization tests before converting, keep conversion commits separate from refactors and features, and review converted code for semantics changes (equals/hashCode, nullability, static initialisation).

What does the automatic converter get wrong?

It produces working but non-idiomatic code: !! and lateinit overuse, Java-style getters, mutable collections, missed data classes and sealed types. It needs a manual idiomatic pass.

Build and team questions

  • Build time: mixed projects compile both languages. Kotlin's K2 compiler and KSP (instead of kapt) help.
  • Team: agree on Kotlin style (official conventions plus a linter), review idioms, and pair on early conversions.
  • Measure progress: the percentage of Kotlin files is a vanity metric. Track crash rate, delivery speed and test coverage in converted areas.

Frequently asked questions

Should we convert everything?

Not necessarily. Kotlin and Java interoperate well. Convert where it pays off, and let stable Java code be.

Can AI tools help migrate?

Yes, for drafting conversions and explanations, with careful review and tests. See AI for Legacy Java.

Conclusion

Strong migration answers combine interop knowledge (platform types, Jvm annotations, exceptions), an incremental strategy with tests and separate commits, awareness of subtle semantic changes, and team practices that keep the codebase consistent.
