Every Android app waits for things: network responses, database queries, file reads, location updates. Do that waiting on the main thread and the UI freezes. Do it with callbacks and the code turns into nested, hard-to-cancel spaghetti. Kotlin coroutines solve both problems, and Flow extends them to values that change over time.

This guide is for developers who know Kotlin basics and have seen viewModelScope.launch without fully understanding what happens inside it. By the end, you'll know how suspension works, what scopes and dispatchers are really for, how cancellation protects you from leaks, how cold and hot flows differ, and how to test all of it.

The problem coroutines solve

Android draws the UI on the main thread. To stay smooth it must finish each frame in roughly 16 ms at 60 Hz, and less on high-refresh screens. A network call can take seconds. Block the main thread that long and the app stutters. Block it for about five seconds and Android shows an "Application Not Responding" dialog.

The traditional fix, background threads with callbacks, works but creates three problems: callback nesting, manual thread switching back to the UI, and no automatic cancellation when the user leaves the screen. Coroutines address all three.

Suspend functions: pausing without blocking

A suspend function can pause its execution and resume later, without blocking the thread it runs on. While it's suspended, waiting for a network response for example, the thread is free to do other work, such as drawing frames.

class UserRepository( private val api: UserApi, // Retrofit interface with suspend functions private val dao: UserDao, // Room DAO with suspend functions ) { // Reads top to bottom like synchronous code, but never blocks the caller's thread. suspend fun refreshUser(id: String): User { val remote = api.getUser(id) // suspends while waiting for the network dao.upsert(remote.toEntity()) // suspends while Room writes on its own executor return remote.toDomain() } }
Main-safety

A suspend function is main-safe when it can be called from the main thread without blocking it. Retrofit and Room suspend functions are main-safe because they move their work to background threads internally. Your own blocking code, such as file I/O or heavy JSON parsing, isn't main-safe until you wrap it in withContext(Dispatchers.IO) or Dispatchers.Default.

Coroutine scopes and structured concurrency

Every coroutine runs inside a scope, and every scope has a lifetime. When the scope is cancelled, all coroutines inside it are cancelled too. This is structured concurrency, and it's the single most important idea for avoiding leaks.

viewModelScopeThe ViewModel (cancelled in onCleared)Loading screen data, user actions

Dispatchers: which thread runs the code

  • Dispatchers.Main: the Android main thread. Use it for UI and lightweight state updates. viewModelScope and lifecycleScope use Dispatchers.Main.immediate by default.
  • Dispatchers.IO: a thread pool for blocking I/O such as files, legacy blocking SDKs and raw sockets.
  • Dispatchers.Default: CPU-bound work such as sorting large lists, parsing big JSON or image processing.
class ReportRepository( private val ioDispatcher: CoroutineDispatcher = Dispatchers.IO, // injectable for tests ) { suspend fun exportCsv(file: File, rows: List) = withContext(ioDispatcher) { // Blocking file I/O is safe here; callers can stay on Main. file.bufferedWriter().use { writer -> rows.forEach { writer.appendLine(it.toCsvLine()) } } } }
Inject dispatchers

Pass dispatchers in through the constructor instead of hard-coding Dispatchers.IO. In tests you can then swap in a test dispatcher and control time precisely.

launch vs async, and running work in parallel

launch starts a coroutine and returns a Job ("fire and forget, but cancellable"). async returns a Deferred<T> whose result you await(). Use async inside coroutineScope to run independent requests in parallel:

fun loadFeed() { viewModelScope.launch { _uiState.update { it.copy(isLoading = true) } try { // Both requests start immediately; total time ≈ the slower one, not the sum. val feed = coroutineScope { val posts = async { repository.getPosts() } val stories = async { repository.getStories() } Feed(posts.await(), stories.await()) } _uiState.update { it.copy(isLoading = false, feed = feed) } } catch (e: IOException) { // If either request fails, coroutineScope cancels the other one too. _uiState.update { it.copy(isLoading = false, error = e.message) } } } }

Cancellation and exceptions

Cancellation in coroutines is cooperative. A coroutine is cancelled at its next suspension point, where it receives a CancellationException. Three rules prevent most bugs:

  1. Don't swallow CancellationException. A blanket catch (e: Exception) catches it too and can keep a cancelled coroutine running. Catch specific exceptions, or rethrow cancellation.
  2. Make long CPU loops cancellable with ensureActive() or yield(), because they have no suspension points of their own.
  3. Use supervisorScope when one child's failure shouldn't cancel its siblings, for example loading independent dashboard widgets.
viewModelScope.launch { try { val result = repository.sync() _uiState.update { it.copy(lastSync = result.time) } } catch (e: CancellationException) { throw e // let cancellation propagate } catch (e: Exception) { _uiState.update { it.copy(error = "Sync failed") } } }

Flow: streams of values over time

A suspend function returns one value. A Flow<T> emits many values over time, such as database rows that change, search results as the user types, or location updates. Flows are cold by default: the code inside flow { } doesn't run until someone collects it, and it runs again for each collector.

@Dao interface NoteDao { // Room re-emits automatically whenever the notes table changes. @Query("SELECT * FROM notes ORDER BY updatedAt DESC") fun observeNotes(): Flow> }

Operators: transforming flows

@OptIn(FlowPreview::class, ExperimentalCoroutinesApi::class) class SearchViewModel(private val repository: ProductRepository) : ViewModel() { private val query = MutableStateFlow("") val results: StateFlow = query .debounce(300) // wait for typing to pause .map { it.trim() } .distinctUntilChanged() // ignore identical queries .flatMapLatest { q -> // cancel the previous search when a new query arrives if (q.isEmpty()) flowOf(SearchUiState.Idle) else flow { emit(SearchUiState.Loading) emit(SearchUiState.Success(repository.search(q))) }.catch { emit(SearchUiState.Error("Search failed")) } } .stateIn( scope = viewModelScope, started = SharingStarted.WhileSubscribed(5_000), // keep alive briefly across rotation initialValue = SearchUiState.Idle, ) fun onQueryChange(text: String) { query.value = text } } sealed interface SearchUiState { data object Idle : SearchUiState data object Loading : SearchUiState data class Success(val products: List) : SearchUiState data class Error(val message: String) : SearchUiState }

StateFlow and SharedFlow: hot flows

Hot flows exist independently of collectors and share emissions among them.

  • StateFlow always has a current value, replays it to new collectors, and skips emissions equal to the current value. It's ideal for UI state.
  • SharedFlow is configurable (replay, buffer) and has no required initial value. Use it for broadcasting events to multiple collectors.
  • stateIn / shareIn convert a cold flow into a hot one, so expensive upstream work such as a database query runs once and is shared.

The differences deserve their own article: see MVVM vs MVI for how state and one-off events are exposed in practice.

Collecting flows safely in the UI

Collecting a flow while the app is in the background wastes resources, and can crash if you touch Views that no longer exist. Use lifecycle-aware collection:

@Composable fun SearchRoute(viewModel: SearchViewModel = viewModel()) { // Stops collecting when the lifecycle drops below STARTED, resumes when it returns. val state by viewModel.results.collectAsStateWithLifecycle() SearchScreen(state = state, onQueryChange = viewModel::onQueryChange) } viewLifecycleOwner.lifecycleScope.launch { viewLifecycleOwner.repeatOnLifecycle(Lifecycle.State.STARTED) { viewModel.results.collect { state -> render(state) } } }

Testing coroutines and flows

The kotlinx-coroutines-test library provides runTest, which skips delay() calls in virtual time, so a test with a 300 ms debounce runs instantly. Replace Dispatchers.Main in tests, because there is no Android main looper on the JVM:

@OptIn(ExperimentalCoroutinesApi::class) class MainDispatcherRule( private val dispatcher: TestDispatcher = UnconfinedTestDispatcher(), ) : TestWatcher() { override fun starting(description: Description) = Dispatchers.setMain(dispatcher) override fun finished(description: Description) = Dispatchers.resetMain() } class SearchViewModelTest { @get:Rule val mainRule = MainDispatcherRule() private val fakeRepo = object : ProductRepository { override suspend fun search(query: String) = listOf(Product("1", "Phone case", 299.0)) } @Test fun `typing a query emits success after debounce`() = runTest { val vm = SearchViewModel(fakeRepo) val states = mutableListOf() // Collect in the background so stateIn's WhileSubscribed upstream is active. backgroundScope.launch(UnconfinedTestDispatcher(testScheduler)) { vm.results.toList(states) } vm.onQueryChange("case") advanceTimeBy(301) // move virtual time past the debounce runCurrent() assertTrue(states.last() is SearchUiState.Success) } }

Frequently asked questions

Are coroutines threads?

No. Coroutines are lightweight units of work that run on threads. Thousands of suspended coroutines can share a small thread pool, because a suspended coroutine doesn't occupy a thread.

Do I still need Dispatchers.IO with Retrofit and Room?

Not for their suspend functions, which are already main-safe. You need it for your own blocking code, such as file access or blocking SDK calls.

When should I use Flow instead of a suspend function?

Use a suspend function for a single result, such as fetching a user. Use Flow when values change over time, such as database observation, location updates or user input streams.

Should I replace RxJava with coroutines?

For new code in Kotlin, coroutines and Flow are the standard choice and integrate with Jetpack. Migrate existing RxJava code gradually. Interop libraries exist to bridge the two.

What does WhileSubscribed(5000) do?

It keeps the upstream flow active for five seconds after the last collector disappears. That's long enough to survive a configuration change such as rotation without restarting expensive work, but it still stops when the user truly leaves.

Conclusion

Coroutines give Android a simple promise: write asynchronous code sequentially, and let scopes clean up after you. Learn suspension and main-safety first, then structured concurrency and dispatchers, then Flow and its operators. Test with runTest and injected dispatchers, and avoid GlobalScope and swallowed cancellations.
