If you open a five-year-old Android project, you'll find activity_main.xml, findViewById or View Binding, RecyclerView adapters and Fragments. Open a project started recently and you'll likely see @Composable functions and no layout XML at all. Both are "Android UI", but they work very differently.

This article is for beginners deciding what to learn and for developers on XML-based apps deciding whether and how to adopt Compose. You'll see the same screen built both ways, understand why Compose behaves as it does, and get a realistic view of performance, interop and migration.

Quick verdict

Which should you learn?

Learn Jetpack Compose first. Google recommends it for new Android UI, new Material 3 components and adaptive layout APIs are Compose-first, and it requires less code for most screens. Learn enough XML to maintain existing screens, because many production apps are partly migrated and will be for years.

Imperative vs declarative: the core difference

With XML Views you build a tree of View objects once (by inflating XML), then mutate them over time: textView.text = ..., button.isEnabled = false, progress.visibility = View.GONE. Your code is responsible for keeping every view consistent with the data. This is imperative UI.

With Compose you write functions that describe the UI for the current state. When state changes, Compose calls the affected functions again. This is called recomposition. It then updates only what changed. You never call setters on widgets. This is declarative UI: UI = f(state).
